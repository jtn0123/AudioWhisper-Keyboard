# Stage 4: Setup

This page covers step 11 of [the Compose removal plan](compose-removal.md). Rust now draws the
first-run setup screen. `SetupScreen`, its `NotificationPermissionState` file and
`FlorisStepLayout` are deleted. Rust decides everything the screen does: which screen a fresh
activity opens, which step is open, what each step's button does, when to ask for the
notification permission and what the answer means, and when setup is finished. Kotlin keeps
only the Android calls Rust cannot make.

| Route | Drawn by | Notes |
| --- | --- | --- |
| `setup` | Rust | New here. The intro, the four steps and the footer. |

The Compose route `Setup.Screen` stays as an empty entry that hands back to Rust, as in steps 2
and 4 to 8. It now carries the deep link `setup`, so the fallback activity, whose start
destination is still `if (isImeSetUp) Home else Setup.Screen`, hands it back like any other
route Rust draws.

## What it shows

The screen FlorisStepLayout drew, in the same order:

1. The intro message, then a 16 dp gap.
2. Four step headers: a 56 dp row with a 40 dp circle holding the step's number and a 32 dp
   pill holding its title. The open step is primary with on-primary ink; the others are
   primary at 38 %; a step not reached yet is at 38 % again.
3. The open step's body under its header, beside the dashed line (2 dp on, 10 dp off, 12 %
   ink): its paragraphs and a filled button, centred. The open step takes the height left
   over, as Compose's `weight(1f)` gave it.
4. The footer: *Privacy policy* • *Repository*, text buttons that open the two URLs.

There is no back arrow (`navigationIconVisible = false`), and Back leaves the app.

| Step | Done when | Button |
| --- | --- | --- |
| Enable AudioWhisper | The keyboard is in the enabled input methods | Opens the system's input method settings (`enable`, the effect the home screen already used) |
| Select AudioWhisper | The keyboard is the default input method | Opens the input method picker (`picker`) |
| Permit notifications | The question was answered, or notifications are allowed | Asks for `POST_NOTIFICATIONS`, or opens the app's notification settings once Android will not ask again |
| Finish up | Never: it is the last | Writes `internal__is_ime_set_up = true` and opens home with nothing to go back to |

Which step is open follows FlorisStepState: the first step not done (`currentAuto`), unless the
user opened an earlier, done step by its header (`currentManual`). A done step's header opens
it; while an earlier step is open, the first undone step's header opens that one again; a step
not reached yet does nothing.

## First-run routing

Every way into settings now opens the Rust host, and Rust picks the first screen with settings
op 40 (START), given the settings link the intent carries, if any. The rules are the ones
`FlorisAppActivity` and `SettingsEntry.rust` applied before, in the same order:

1. A notification question never answered (`NOT_SET`) sends a user who finished setup through
   it again: `internal__is_ime_set_up` is written `false`. FlorisAppActivity did this on every
   start.
2. A settings link opens its screen, with home under it, even during setup. The Rust host
   opened for a link before as well.
3. With no link, setup opens until it is finished.
4. Otherwise home opens.

A later intent (`onNewIntent`) navigates to its link, and a `SEND` or `VIEW` intent that is not
a settings link (an extension file) goes to the Compose fallback activity, both as before. A
recreated activity restores its saved stack and does not START again.

`SettingsEntryTest` checks the four rules through the natives, with the intents the app sends
and declares: the launcher's `MAIN`, the keyboard's settings button (no action), a
`ui://florisboard/…` link and an extension file.

## The boundary

All of it is generated by `wire`'s `declare!` (`wire::settings_ui::setup`); no `external fun`
was written by hand.

* **Op 40, `START`:** no fields, or the route a settings link named.
* **Op 41, `PERMISSION`:** `SettingsUiPermission`, the request's answer: `GRANTED` and
  `RATIONALE`, each `true` or `false`. Anything else is refused with `IllegalArgumentException`.
* **Effects, `SettingsUiSetupEffect`:** `askNotifications`, `notificationSettings` and
  `setupReturn`. The screen also uses the existing `enable`, `picker`, `url`, `write` and
  `finish`.
* **Facts, `SettingsUiSetupFact`:** `notifications_granted` and `notifications_rationale`, sent
  with every FACTS report, which RustSettingsView sends on each resume.
* **CONFIG:** fields 10 and 11, whether the keyboard is enabled and selected, were already
  there; Rust now works the steps out from them.
* **Saved state:** version 7 adds a 20th field, `manual|away|first`: the step opened by its
  header and the step the user was sent to the system for (numbers from 1, 0 for none), and
  whether that was the first undone step. Setup, like home, is restored only at the bottom of
  the stack.

## Data path

| Direction | What | When |
| --- | --- | --- |
| Kotlin → Rust | CONFIG with the keyboard enabled and selected | Each configure, and now each time `Settings.Secure`'s enabled or default input method changes |
| Kotlin → Rust | FACTS with the two permission facts | Each resume |
| Kotlin → Rust | PERMISSION with the request's answer | When Android's dialog closes, also into an activity recreated meanwhile |
| Kotlin → Rust | START with the link | A fresh activity, once its host is bound |
| Rust → Kotlin | `write` of the two preferences | The answer stored, setup reset or finished |
| Rust → Kotlin | `askNotifications`, `notificationSettings`, `setupReturn`, `enable`, `picker`, `url` | A tap, or the keyboard enabled while the user is in the system's settings for it |

The stored values are Compose's, in the same preferences: `internal__notification_permission_state`
is `NOT_SET`, `GRANTED` or `DENIED`, and `internal__is_ime_set_up` is `true` or `false`. Rust
reads and writes them as text through the existing `write` effect. The enum moved into
`AppPrefs.kt`, because the preference model still declares the preference with it and
`SettingsDefaultsMatchTest` compares how the old and native declarations read stored text.

How Rust reads the notification step (`Notice`):

* allowed now (the fact), or `GRANTED` stored with no fact yet: **granted**;
* otherwise `NOT_SET`: **unasked**, the step is still to do;
* `DENIED` while Android would ask again (`notifications_rationale` true): **denied**;
* `DENIED` otherwise: **blocked**, Android shows no dialog any more.

## Kotlin added or kept

* **`SettingsSetup.kt`** (new, 59 counted lines). It must be Kotlin: it registers the permission
  request with the activity's `ActivityResultRegistry`, reads the permission with
  `ContextCompat.checkSelfPermission` and `ActivityCompat.shouldShowRequestPermissionRationale`,
  starts `ACTION_APP_NOTIFICATION_SETTINGS` and FlorisAppActivity with `startActivity`, and
  watches `Settings.Secure` with a `ContentObserver`. All are Android calls. It decides nothing:
  each effect maps to one call, and each answer is passed on as it came.
* **`SettingsSetupStringIds.kt`** (new, 28 counted lines). The screen's `R.string` ids, as each
  Rust screen has. `R` is generated for Kotlin and Java. They are a file of their own because
  `SettingsStringIds.kt` is at 497 of its 500 counted lines.
* **`RustSettingsView.kt`** (255 to 260 counted lines; the ledger notes why). It creates
  `SettingsSetup`, sends START, hands it the three effects and adds its facts to each report.
* **`FlorisAppActivity.kt`** (258 to 249). It installs the Rust host whenever Rust is allowed,
  and sends START on a fresh activity; the `NOT_SET` reset and the hand-over from Compose's setup
  to the Rust host are gone.
* **`SettingsEntry.kt`** keeps only `linkRoute`; `rust()` is gone.

## Improvements

1. **Notifications already allowed skip the question.** Compose asked even when the permission
   was granted, for example on Android 12, which has no such permission and reports whether
   notifications are on, or when they were allowed before setup.
   Rust stores `GRANTED` on setup as soon as a report says notifications are allowed, and the
   step is done. Tests: `notifications_already_allowed_skip_the_question`,
   `notificationsAlreadyAllowedSkipTheQuestion`.
2. **A denial for good opens the notification settings.** Once Android stops asking, Compose's
   *Grant Permission* did nothing, because Android drops the request. Rust shows "Notifications
   are off." and an *Open Notification Settings* button that opens the app's page there; allowed
   there, the next report stores `GRANTED`. A denial Android would ask again keeps the grant
   button. The step's status line also says when notifications are allowed. Tests:
   `the_permission_answer_decides_what_the_step_shows_next`,
   `aDenialForGoodSendsTheUserToTheNotificationSettings`.
3. **Plain-language steps for TalkBack.** Compose's headers were clickable boxes that read only
   the number and the title, and a later step's header was clickable too: it did nothing then,
   but remembered the step and opened it once the earlier steps were done. Each header now
   reads "Step 2 of 4: Select AudioWhisper" with its state (*Done*, *Current step*, *Up next* or
   *Not yet: finish the steps above first*); the open one is a heading, a header a tap opens is a
   button, and a later one is plain text with no action. The status line is a polite live
   region, so the answer is announced. Tests: `headers_read_their_number_state_and_whether_a_tap_opens_them`,
   `headersReadTheirStateAndADoneOneOpensAgain`, `aDenialForGoodSendsTheUserToTheNotificationSettings`.
4. **Back from the system with the step done opens the next step.** A user who reopened a done
   step and pressed its button stayed on that step in Compose after coming back, because the
   manual step stayed chosen. Rust clears it when the step the user went for is done (or, for the
   question, answered). Back with the step still not done, it stays open. Tests:
   `back_from_the_system_with_the_step_done_opens_the_next_even_when_reopened`, and the
   `away` assertion in `the_permission_answer_decides_what_the_step_shows_next`.
5. **The keyboard is noticed when it changes, not by polling.** Compose checked whether the
   keyboard was enabled every 200 ms for as long as the screen was composed. A `ContentObserver`
   on the two `Settings.Secure` keys now sends CONFIG when either changes. This is Android-only;
   the emulator check below shows the app coming back.

## Differences from Compose

* Paragraphs are ragged right; Compose's `StepText` was justified.
* The whole screen scrolls when the open step does not fit. Compose scrolled the open step's
  content inside its weighted box.
* Nothing animates: a step opens and closes at once, where Compose animated its weight and
  visibility. No Rust settings screen animates yet ([owed-checks](owed-checks.md#not-device-checks-but-still-owed)).
* The app brings itself back once the keyboard is enabled only when the user went to the
  system's settings from the Enable step's button. Compose came back whenever the Enable step
  was the automatic one, no step was chosen and nothing else was done, however the keyboard got
  enabled.
* The first permission dialog closed without an answer (Back, or a tap outside, on Android 13
  and later) reports a denial with no rationale, so it reads as blocked and the button opens the
  notification settings. Compose stored `DENIED` the same way and then could not ask again.
* Until the first FACTS report, a stored `DENIED` reads as blocked. The report comes on resume,
  before the user can tap.
* A step not reached yet is plain text, not a disabled button: Rust exposes every `text` node as
  enabled, so it says so in its state instead.
* As on every Rust screen, controls scrolled fully out of view are not in the TalkBack tree;
  TalkBack scrolls to reach them.
* An extension file opened before setup is finished opens in the fallback activity over setup,
  as it does after setup. Compose opened its import screen in setup's place.
